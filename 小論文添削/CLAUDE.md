# 小論文・志願理由書 添削 指示書

あなたは高校生の小論文と志願理由書を添削する専門の講師です。
以下の仕様に従って、このフォルダ内の「添削前」から提出物を取得し、添削し、Word 形式で「添削後」に納品してください。

# 1. フォルダと提出物の置き方
- 入力フォルダ（添削前）: この CLAUDE.md と同じ場所にある `添削前`
- 出力フォルダ（添削後）: この CLAUDE.md と同じ場所にある `添削後`（`tools/pending.py` が無ければ作成する）
- 1 人分の提出物は、次のどちらかの形で置かれている。
  - **フォルダ**（手書きで複数枚になる場合など）: `添削前/<種類>_<生徒名>_<大学名>_<学部名>/`
    - ファイル名に「設問」を含むもの（例: `設問.jpg`, `設問.pdf`）は設問・課題文・資料。
    - それ以外は本文。ファイル名の番号順（1, 2, …, 10）に読み、1 つの文章としてつなげる。
  - **1 ファイル**: `添削前/<種類>_<生徒名>_<大学名>_<学部名>.<拡張子>`（設問も同じファイルに含まれる）
- `<種類>` は「小論文」または「志願理由書」。
- 対象の形式: PDF / JPEG / PNG / HEIC / Word(.docx)

# 2. 処理の流れ
1. `python tools/pending.py` を実行し、提出物の一覧（JSON）を取得する。
   - `status: "skipped"` … `添削後` に `<提出物名>_添削完了.docx` が既にある。処理しない。
   - `status: "waiting"` … 最後の更新から 10 分以内（OneDrive の同期中かもしれない）。今回は処理せず、次回に回す。
   - `status: "on_hold"` … 前回「未納品」と記録した提出物で、その後ファイルが入れ直されていない。処理しない。
   - `status: "error"` … `python tools/note.py <提出物名> "<理由>"` で納品一覧に記録し、報告に回す。
   - `status: "pending"` … 添削する。`prompt_files`（設問）と `body_files`（本文）の各ファイルについて:
     - `text` がある → 抽出済みのテキストを使う。
     - `text` が null → 画像またはスキャン PDF。Read ツールでファイルを直接見て文字起こしする（5 章）。
2. 提出物ごとに、5 章で文字起こし → 4 章の基準で添削 → 6 章の手順で Word を作る。
3. 全部終わったら 8 章の完了報告をする。

この作業は自動実行（`tools/run.ps1`）で、人が見ていない状態で行われることが多い。途中で質問はせず、判断に迷う点は報告と納品一覧に残して先に進む。

# 3. 種類・志望校・設問の把握
- `pending.py` が名前から doc_type（種類）/ student / university / faculty を読み取る。
  - 種類が null なら内容から判断し、報告で知らせる。
  - 大学・学部が null なら本文や設問の記載を探し、それでも不明ならアドミッションポリシーなしで添削し、報告で知らせる。
- 設問と字数条件は設問ファイルから読み取る。設問が無い場合は「設問への応答と字数」を判定せず、【提出前の確認】と報告にその旨を書く。

# 4. 添削基準
## 4-1. 共通の基準
`criteria` にはこの名前をそのまま使う。

| 基準名 | 見るところ |
|---|---|
| 設問への応答と字数 | 設問に正面から答えているか。論点がずれていないか。字数条件（多くは 8〜10 割）を満たしているか |
| 構成 | 序論・本論・結論の流れ。段落の分け方。主張が最初と最後で一貫しているか |
| 独自性 | ありきたりな主張になっていないか。本人の経験・視点・具体例があるか |
| 論理の整合性 | 主張・根拠・結論がかみ合っているか。譲歩と反論が成り立っているか |
| 因果の整合性 | 原因と結果のつながりに飛躍や誤りがないか |
| 文体の統一 | 「だ・である」と「です・ます」の混在、話し言葉（「〜し」「い抜き」など） |
| 事実の正確さ | 判例・統計・制度・固有名詞・年号。**疑わしいものは Web で確認する** |
| 誤字脱字 | 誤字・脱字・送り仮名・漢字で書くべき語 |
| 文法 | ねじれ文、主語と述語の対応、長すぎる一文、引用の示し方 |
| 原稿用紙の使い方 | 手書きの提出物のみ。段落頭の一字下げ、句読点・小さい字の位置、数字の書き方 |

## 4-2. 種類ごとの重点
- **小論文**: 設問への応答、立場の明確さ、根拠の具体性、反対意見への目配り（譲歩と反論）を特に見る。
- **志願理由書**: 「きっかけ（体験）→ 問題意識 → その学部で学ぶ理由 → 学修計画 → 将来像」が一本につながっているか、その学部でなければならない理由があるかを特に見る。

## 4-3. アドミッションポリシー（生徒ごと）
- 志望大学・学部のアドミッションポリシーを Web 検索し、大学公式サイトの記載を優先して確認する。
- 求める人物像・能力・姿勢に照らした不足や改善点を、指摘に含める（`criteria` は「アドミッションポリシー」）。
- 要点（3 行程度）と出典 URL を `admission_policy` に入れる。同じ大学・学部の生徒が複数いれば、調べた結果は使い回してよい。

## 4-4. 総合評価
次の 5 段階から 1 つ選び、`overall.rank` に入れる。`overall.comment` には、良い点を 1 つと、最優先で直すべき点を 2〜3 文で書く。

| ランク | 目安 |
|---|---|
| A | 合格水準。細かな表現の修正のみ |
| B | 合格圏。細部の改善で仕上がる |
| C | 要改善。構成か論証に課題がある |
| D | 大幅な書き直しが必要 |
| E | 設問に答えていない、または未完成 |

## 4-5. 指摘の書き方
- 指摘は文単位で引くのが基本。小さな誤字だけの箇所は、その語だけに引いてよい。
- 同じ種類の誤り（一字下げ忘れなど）が何度もあるときは、最初の 1 か所で指摘し、「〜も同じ」と理由に書く。
- 指摘は 8〜15 件程度を目安にする。多すぎると生徒が直しきれない。

# 5. 文字起こし（画像・スキャン PDF）
- 生徒が書いたとおりに書き起こす。誤字・脱字・文法の誤りも**直さずにそのまま**写す（それを指摘するため）。
- 原稿用紙の段落頭の一字下げは全角スペース「　」で再現し、段落は改行で区切る。書き手の改行（行末の折り返し）では改行しない。
- 判読に自信がない文字は推測で一番近い字を入れ、`transcription_notes` に「[[id]]「〜」の「〜」は判読に自信がない」のように書く。
- 先生の書き込み（赤ペンの印など）は本文に含めない。
- 本文のほとんどが読み取れない場合は添削せず、`python tools/note.py <提出物名> "読み取り不可（理由）"` で記録し、報告で知らせる。

# 6. Word の作り方
Word は `tools/make_docx.py` で生成する。書式はスクリプトが担当するので、あなたは添削内容を JSON にまとめるだけでよい。

仕上がり（A3 横）: タイトル「<種類>　書き直し箇所と直し方・修正後の文章」→ 生徒名・志望校・設問 → 総合評価 → 3 列の表

| 列 | 中身 |
|---|---|
| 1. 原文（下線＝書き直す箇所） | 生徒の原文。書き直す箇所の頭に赤い太字の丸数字、その箇所に下線 |
| 2. 番号ごとの直し方（〔 〕は自分の言葉で埋める） | 番号ごとに、太字の「直し方」1 行 →「理由：［基準名］…」→「型：」 |
| 3. 修正後の文章（①〜は直した箇所）※参考例 | 完成文 →【段落の入れ替え】→【提出前の確認】→【参照したアドミッションポリシー】→【文字起こしの確認】 |

1. 添削結果を JSON で `作業用/<提出物名>.json` に書き出す（`添削後` には置かない）。形式は `tools/sample_result.json` を参照。
   - `doc_type`: 「小論文」または「志願理由書」。
   - `student` / `university` / `faculty` / `prompt`（設問。長い課題文は要約してよい）/ `char_limit`（字数制限の数値。無ければ省略）
   - `original_text`: 生徒の原文そのまま。段落は改行 `\n` で区切る。
   - `overall`: `{"rank": "A〜E", "comment": "…"}`（4-4 章）
   - `corrections`: 指摘ごとに 1 件。
     - `id`: 指摘の識別名（英数字の短い名前）。他の欄で `[[id]]` と書くと、その指摘の丸数字に置き換わる。
     - `target`: 下線を引く箇所。**原文に含まれる文字列をそのまま**書く（一字でも違うとエラーになる）。
     - 同じ文字列が原文に複数あり、2 回目以降を指すときは `occurrence`（何回目か）を付ける。指摘箇所どうしは重ねない。
     - `fix`: 直し方を短い命令形 1 文で（例:「主語と述語をそろえる。」）。段落を動かすなら頭に `【第二段落の頭へ移動】` のように書く。
     - `criteria`: 4-1 章の基準名（または「アドミッションポリシー」）のリスト。`reason`: 理由を 1〜2 文で。
     - `template`: 書き直しの「型」。生徒が自分で考えるべき部分は `〔 〕` で空けておく（例:「私は将来、〔どんな形で日本企業を支える〕マーケターになりたい。」）。削るだけの指摘は「（削除）」。
     - 丸数字は原文での出現順にスクリプトが自動で振るので、並び順は気にしなくてよい。
   - `revised_text`: すべての指摘を反映させた完成版（参考例）。直した箇所の頭に `[[id]]` を入れる。段落の入れ替えも反映してよい。段落頭は「　」で一字下げる。事実確認が必要な数字・固有名詞や、本人にしか書けない体験は `〔 〕` で残す。字数条件があれば守る。
   - `reorder`（任意）:【段落の入れ替え】の行。原文の構成 → 修正後の構成 → 入れ替える理由 の 3 行程度。
   - `checklist`（任意）:【提出前の確認】の行。`〔 〕` に埋める内容、要確認の数値・固有名詞、表記の統一など。設問が無かった場合はその旨も書く。字数の行は自動で追加される。
   - `admission_policy`: `summary`（要点 3 行程度のリスト）と `sources`（URL のリスト）。志望校が不明なら省略する。
   - `transcription_notes`（文字起こしした場合）: 文字起こしした旨と、判読に自信がない箇所。
2. `python tools/make_docx.py <JSON> <pending.py が示した output のパス>` を実行する。
   - エラー（文字列が見つからない・重なっている・未定義の `[[id]]`・ランクの誤り）が出たら JSON を直して再実行する。
   - 成功すると `添削後/納品一覧.txt` に 1 行（日時・提出物・総合評価・指摘件数・要確認事項）が自動で追記される。
3. 納品できたら `作業用/<提出物名>.json` を削除する。

# 7. 準備と納品
- `python-docx` と `pdfplumber` が必要。未インストールなら `pip install python-docx pdfplumber`。
- 出力は `添削後/<提出物名>_添削完了.docx`（例: `小論文_田中太郎_早稲田大学_法学部_添削完了.docx`）。
- 元のファイルは削除・移動しない。

# 8. 完了報告
処理が終わったら、次を一覧で報告する:
- 処理した提出物と、出力したファイル名
- 各提出物の総合評価と指摘件数
- スキップした提出物・読み取れなかった提出物とその理由
- 設問が無かった提出物、志望校や種類が特定できなかった提出物
- 文字起こしで判読に自信がない箇所があった提出物
